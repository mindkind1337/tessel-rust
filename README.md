# Tessel Rust

Native Rust rewrite of Tessel. The application UI and backend are pure Rust over a shared core (`app::Tessel`), pairing a native GPU-accelerated **GPUI** primary renderer (`DirectX` / `Metal` / `Vulkan` with DirectWrite subpixel text and `resvg` vector icons) with a universal **`eframe`/`egui`** OpenGL Compatibility renderer (`--renderer gpui` / `--renderer compat`, `TESSEL_RENDERER`, `Settings > Appearance`, and automatic runtime fallback on older GPUs or Remote Desktop). No Electron, Vue or Node application runtime is bundled. External shells and agent CLIs remain separate programs; the Windows browser uses Microsoft's WebView2 engine.

The migration targets identical Tessel appearance, layout, menus, shortcuts and behavior across the GPUI and Compatibility renderers. Full parity is not yet verified: some SSH integrations remain unwired, and passing model/UI suites does not replace native end-to-end acceptance.

## Features

- Local and SSH HTML previews show the project-relative page path with controls to reload, open in the browser, and manage folder trust.

- Switching HTML editor tabs keeps recent drafts available to links in the same project preview. Opening that page in the owner browser preserves its address and linked drafts, including subsequent preview updates.

- HTML previews share four background workers for SSH project assets across browser tabs. Local previews have their own queue.

- Git worktree bases accept local or remote branch names and full SHA-1/SHA-256 commit identities. Tags and abbreviated revision expressions are rejected; a hex-named branch cannot substitute a different commit for a requested full identity.

- Live Share excludes the protected Linear credential file (`linear.dat`) from guest browsing and access, including a copy placed inside a shared project. Both renderers now open an owner-local Linear dialog from the command palette, grouped Issues toolbar menu or toolbar overflow menu, with an encrypted account connection, team/state filters, issue details, refresh, copy/open actions and confirmed disconnect. Keys stay out of workspace state, snapshots and shared messages.
- Linear issues can start a new local native Codex or Claude task from either renderer, with an optional isolated Git worktree. The dialog captures its project and account; external-issue launches disable optional environment-file copying and setup execution. An explicitly chosen Linear state is applied only after the first native turn is submitted. A state-update failure produces a warning without retrying the task. Terminal-agent and remote/guest issue launches remain unported.

- Legacy `#n` agent addresses use saved project-scoped member numbers rather than internal pane identifiers. Existing numbers survive reordering and restart; newly opened panes receive a free number. `team_members` includes the number alongside the pane identifier, and `pane:<id>` remains an explicit address. Cross-project relay refuses ambiguous numeric aliases instead of choosing a recipient.

- Stored task prerequisites remain blocking when a required card is deleted or reopened. Agent moves to Doing, Review or Done respect those prerequisites; the user can still override the column manually. Restoring a workspace remaps both live and missing prerequisite identifiers. `team_tasks` reports prerequisite and waiting identifiers. When a To do card's prerequisites become complete, its assigned teammate receives a mailbox notice once per observed transition. The saved readiness state prevents repeated notices on refresh or reload; mailbox delivery itself is not durable across a process crash. Editing dependency links in the UI remains unfinished.

- Native Codex's task tools accept `team_task_add`, `team_tasks`, `team_task_move`, `team_task_done` and `team_task_gate`, with string card identifiers and the `todo`, `doing`, `review`, and `done` column names. Creation accepts a teammate name or `#n` and up to ten existing prerequisite card ids in `after`; unfinished prerequisites place the new card in To do. Assignment and prerequisites save together before success is returned. Listing includes assignees, stored reports and task creators. The optional `me` label cannot change the calling pane or project. The older `tessel_*` tools remain available.

- Local agents can save a succeeded/failed report with a summary and file paths. Success moves the card to Done only when prerequisites and current review gates permit it; a blocked report remains saved, and failed reports retain the current column. The task giver receives a team mailbox notice after persistence. Paths are inert report text, not file-access authority. Reports survive reload; settings restore preserves report text while clearing old pane attribution. Both boards show collapsible reports with the outcome, summary and file list. Report text and paths currently remain plain, inert content; rich formatting, context-aware file opening and remote report provenance are still being ported.

- Task decision questions, choices and user answers survive restart. Pending questions block agent advancement and successful completion. Both renderers offer explicit choice buttons and a freeform answer; leaving the input does not submit it. A replaced question rejects stale answers, and restored settings require a fresh answer rather than reusing an imported approval. The asking teammate receives a mailbox notice after the answer is saved. Guest answers through Live Share and native attention notifications remain unfinished.

- Stopping a native Claude connection during account validation cancels the remaining startup work before launching its process. A process already starting is still cleaned up when its cancelled connection owner is dropped.

- Both GPUI and Compatibility process queued worker launches through the shared application loop, rechecking the project, team, coordinator and working folder before creating a pane. Cancelling removes queued launches, and a failed pane creation reports failure without renaming or binding an existing pane. A matching coordinator worktree is retained. Successful binding places the frozen assignment once in the worker's team inbox, without typing it into a terminal. Native Codex workers automatically submit their first turn once the account and connection are ready, retaining the owner's draft and the normal sandbox/approval policy. A changed context, connection failure or timeout is reported without automatic retry; an already-used chat is not interrupted. The team tools expose first-turn status. Stop requests from the team tools and UI also stop native chats; Release cancels a pending automatic first turn but keeps the chat available. Team-tool transport and automatic startup for terminal agents and Claude chat are still being integrated.

- The Past conversations command opens a standalone dialog in GPUI and Compatibility. GPUI reuses the existing history search, profile-aware resume and deletion confirmation, works with the side panel closed, and rejects delayed search edits after closing or switching context. Its native search keeps selection, clipboard, undo and IME behavior; Escape clears the query first and closes the dialog once the query is empty.

- Removing a past conversation requires confirmation and revalidates its local account, transcript path and provider identity before asking Windows to recycle the file. Open panes, unknown entries, linked paths and changed Codex metadata are refused. Recycling runs in the background and reports cancellation or failure; it no longer directly deletes transcript files.

- Local Claude and Codex terminal and native-chat conversations retain their original account when resumed, even after another account is selected. Past conversations identifies each profile and resumes in the current workspace with the conversation's original working folder. Older saved panes recover their account in a bounded background scan only when exactly one known profile matches; missing, ambiguous or unavailable profiles stop with an error instead of starting a replacement conversation. Profile bindings contain no credentials and are excluded from portable backups and sync. Switching between terminal and native chat keeps the conversation and its account, waits for the terminal to stop, and refuses a switch while a process is starting. Native startup validates the original transcript in the background and never connects restored panes automatically. Relative custom profile paths must still resolve to the original root.

- Owner-only Windows account panel with external-browser PKCE sign-in, bounded HTTP requests, explicit verification, strict boolean `admin` gating for the `admin.tesselcode.com` `Administration` portal shortcut, and sign-out. ## Run and verify

Install Rust stable and native C/C++ build tools. Windows requires MSVC build tools, the Windows SDK and WebView2 Runtime. Agents, Git and OpenSSH must be installed separately for their corresponding features.

```sh
cargo run --locked -j 2
cargo run --locked -j 2 -- --renderer compat
cargo fmt --check
cargo test --locked -j 2 --all-targets -- --test-threads=2
cargo clippy --locked -j 2 --all-targets --all-features -- -D warnings
cargo build --locked -j 2
```

Windows executable: `target/debug/tessel-rust.exe`. Launch defaults to the hardware-accelerated **GPUI** renderer (`--renderer gpui` / `TESSEL_RENDERER=gpui`); pass `--renderer compat` or set `TESSEL_RENDERER=compat` (or switch under `Settings > Appearance > UI Renderer`) to force the universal OpenGL Compatibility renderer, which is also used automatically as a runtime fallback if GPU window initialization fails. CI produces an optimized portable ZIP with its checksum; no installer or product release is published yet. `--data-dir <folder>` selects a separate workspace metadata directory for testing.

The Git build label tracks commits without forcing recompilation when optional Git reference files are absent. Two test threads keep synthetic child-process timing checks from competing with the entire suite at once.

Optional native acceptance checks:

```powershell
.\target\debug\tessel-rust.exe --self-test-browser
.\target\debug\tessel-rust.exe --self-test-agent-browser
.\target\debug\tessel-rust.exe --self-test-codex
.\target\debug\tessel-rust.exe --self-test-vault
.\target\debug\tessel-rust.exe --self-test-pdf
.\target\debug\tessel-rust.exe --self-test-office
```

The browser check creates a local HTTP fixture and temporary browser profile, downloads direct, cookie-authenticated and blob PDFs, and compares all saved bytes to the original synthetic PDF. Both browser checks also cancel a deliberately slow transfer after observing native progress and verify that an incomplete response cannot report completion and is stopped by the stall guard (three seconds in the fixture, 120 seconds normally). It uses no personal account. The agent-browser check repeats those original downloads with tool-selected names, checks returned paths/status, exercises snapshot/fill/click/select/check/scroll and a real nonblank PNG screenshot with project/origin rejection, refuses origin mismatch and password-field entry, and checks cookie isolation against a separate profile. The Codex check initializes the real installed app-server and verifies its applied permissions and probes history compatibility; it sends no prompt or model turn. The PDF check renders two synthetic original pages in the resource-limited worker and rejects invalid input. The Office check decodes synthetic DOCX and XLSX files through the actual isolated worker, checks original text/cached values and refuses damaged/cancelled input. The vault check uses a temporary profile and an in-process synthetic HTTPS site, without real credentials or network access. Credential fill runs in an isolated WebView2 JavaScript world, with fixed success/refusal results and cancellation when its pending request is dropped. The native check also poisons page-world URL and setter lookup functions and verifies that they cannot bypass the isolated guards. It checks form ownership, cross-origin actions and submit-button overrides (including external controls), changes triggered while filling the username, relative actions under a foreign base URL, and action-property shadowing; no form is submitted. `cargo build --features visual-test` enables eframe's screenshot test support.
